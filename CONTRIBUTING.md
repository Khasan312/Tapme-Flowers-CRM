# Как работать с Git в Tapme Flowers

Эти правила действуют для всех участников проекта. Обычная задача проходит путь:

**Ветка от `develop` → PR в `develop` → PR `develop` в `main` → новый релизный тег → production.**

Отдельную ветку `release` не создаём. Срочное исправление выпускаем по процедуре
hotfix ниже. Рабочий адрес CRM: <https://tapme.kg/crm-flowers/>.

## Назначение веток

| Ветка | Для чего | Как вносим изменения |
| --- | --- | --- |
| `develop` | Общая версия для разработки и следующего выпуска | Через PR из рабочей ветки |
| `main` | История версий, допущенных к production | Через PR из `develop` или hotfix-ветки |
| `feature/<задача>` | Новая функция | Создаём от актуального `origin/develop` |
| `fix/<задача>` | Обычное исправление | Создаём от актуального `origin/develop` |
| `docs/<задача>` | Документация | Создаём от актуального `origin/develop` |
| `hotfix/<задача>` | Срочное исправление production | Создаём от текущего production-коммита |

Ветки автоматизированных задач могут иметь префикс `codex/` и проходят тот же PR-процесс.
`main` может содержать ещё не выпущенные изменения: фактическую production-версию
определяют успешный деплой, его тег и состояние на сервере.

## Правила команды

- Прямые push в `main` и `develop` запрещены. Все изменения, включая документацию,
  проводим через PR.
- Одна рабочая ветка и один PR решают одну задачу. Указываем понятное имя ветки,
  например `feature/order-reminders` или `fix/payment-deadline`.
- Заголовок PR начинаем с `CRM-`, затем описываем результат:
  `CRM-добавить напоминания о заказе`. Если есть номер задачи, указываем его.
- В описании PR пишем, что изменилось, как проверено и нужны ли миграции или
  изменения окружения. При изменении интерфейса прикладываем снимок экрана.
- Перед слиянием запрашиваем ревью коллеги и разбираем замечания. Не сливаем PR
  с красными или незавершёнными обязательными проверками.
- Используем **Merge pull request** с merge commit. Особенно важно сохранять
  историю при объединении `develop → main`, hotfix → `main` и `main → develop`.
- Не переписываем общую историю: без force push, удаления общих веток,
  перемещения и переиспользования опубликованных тегов.
- Пароли, SSH-ключи, `.env`, токены, базы, резервные копии и пользовательские
  файлы в Git не добавляем. Примеры настроек храним без секретов в `.env.example`.

## Один раз после клонирования

```bash
git clone https://github.com/Khasan312/Tapme-Flowers-CRM.git
cd Tapme-Flowers-CRM
git fetch origin
git switch develop
```

В новом клоне без собственных хуков включаем локальный запрет прямого push:

```bash
git config --local core.hooksPath .githooks
```

Хук `.githooks/pre-push` уже исполняемый и блокирует обе общие ветки. Если у вас
есть свои хуки или уже настроен `core.hooksPath`, сначала объедините правила,
чтобы не отключить существующие проверки. Настройка хука у каждого участника
локальная и не переносится через обычный `git clone`.

На текущем тарифе приватного репозитория GitHub не позволяет включить серверную
защиту веток. Поэтому правило команды и локальный хук обязательны; GitHub пока
не гарантирует запрет прямого push и не требует approval технически.
Конфигурации будущей серверной защиты и способ их включения описаны в
[правилах релизов](docs/RELEASES.md#защита-main-и-develop).

## Обычная задача: от ветки до develop

Сначала сохраните свои изменения и убедитесь, что `git status` показывает чистую
рабочую папку. Для каждой новой задачи берём актуальный `develop`:

```bash
git fetch origin
git switch develop
git pull --ff-only origin develop
git switch -c feature/order-reminders
```

Вносим изменения, запускаем подходящие проверки из [README](README.md),
проверяем diff и коммитим только файлы своей задачи:

```bash
git status
git diff
# Вместо путей ниже укажите файлы своей задачи.
git add frontend/src/reminders.tsx backend/tapme/reminders/api.py
git diff --cached
git commit -m "CRM: добавить напоминания о заказах"
git push -u origin feature/order-reminders
```

Открываем PR в GitHub:

- **base:** `develop`;
- **compare:** своя рабочая ветка;
- заголовок: `CRM-добавить напоминания о заказах`.

Чтобы добавить исправления по ревью, делаем новые коммиты и обычный `git push`
в ту же рабочую ветку: PR обновится автоматически. Если `develop` ушёл вперёд,
находясь в своей ветке, подтягиваем его и разрешаем конфликты локально:

```bash
git fetch origin
git merge origin/develop
# При конфликтах исправьте файлы, выполните git add и завершите merge-коммит.
git push
```

После ревью и успешных проверок сливаем PR кнопкой **Merge pull request**.
Затем обновляем локальный `develop`:

```bash
git switch develop
git pull --ff-only origin develop
```

Слияние в `develop` не обновляет production.

## Что должно пройти в Actions

Для PR в обе общие ветки обязательны:

1. **Tests and checks** — серверные тесты, Ruff, mypy, проверка миграций,
   Prettier, сборка TypeScript/Vite и проверки скрипта деплоя.
2. **Build api image** — сборка образа API.
3. **Build web image** — сборка сайта, проверка Caddy и переноса JS/CSS
   через настоящий Compose init с сохранением файлов предыдущего выпуска.

Браузерные E2E запускаем отдельно при изменении пользовательских сценариев;
полный прогон Playwright пока не включён в GitHub Actions. Зелёный CI не заменяет
проверку самой изменённой функции. Если какой-то шаг упал, смотрим его лог,
исправляем причину и дожидаемся нового успешного запуска.

## Плановый релиз на production

1. Убеждаемся, что нужные задачи уже слиты в `develop`.
2. Открываем PR: **base `main`, compare `develop`**.
3. Дожидаемся ревью и трёх успешных проверок, сливаем через **Merge pull request**.
4. Обновляем ссылки и выбираем новое имя тега. Например, для первого планового
   выпуска дня `release-2026-10-19`; для следующего в тот же день — суффикс `.1`.
   Подставьте реальную дату своего выпуска:

   ```bash
   git fetch origin main --tags
   release_day="$(date +%F)"
   release_tag="release-${release_day}"
   git ls-remote --tags origin "refs/tags/${release_tag}*"
   ```

   Если имя уже занято, задайте свободный суффикс в `release_tag`, например
   `release-2026-10-19.1`. Перед следующими командами проверьте коммит:

   ```bash
   git show --no-patch --oneline origin/main
   git tag -a "$release_tag" origin/main -m "CRM release ${release_tag}"
   git push origin "refs/tags/${release_tag}"
   ```

   **Последняя команда запускает production-пайплайн.** Дату в теге используем
   как номер версии: она не откладывает запуск до указанного дня.
5. Дожидаемся успешного **Deploy production**. Проверяем
   <https://tapme.kg/health/> и вход/основные разделы
   <https://tapme.kg/crm-flowers/>. Тег без успешного деплоя ещё не означает выпуск.
6. Добавляем описание GitHub Release для уже отправленного тега. Создание
   описания само по себе повторный деплой не запускает.
7. Синхронизируем `main` обратно в `develop` через PR: **base `develop`, compare `main`**.

Отправляем только конкретный тег. `git push --tags` может случайно отправить
другие локальные релизные теги и запустить лишние деплои.

## Hotfix: срочное исправление production

Hotfix проходит PR и проверки, но не ждёт готовности других задач в `develop`.

1. На сервере узнаём текущую выпущенную версию:

   ```bash
   cat /srv/tapme/state/release
   cat /srv/tapme/state/current
   ```

   Первый файл содержит тег и SHA, второй — слот и SHA. Сверяем их с последним
   успешным **Deploy production** в Actions. Получаем тег локально и создаём
   ветку от него; в примере замените `production_tag` актуальным значением:

   ```bash
   git fetch origin --tags
   production_tag="hotfix-release-2026-10-18.1"
   git switch -c hotfix/fix-order-payment "$production_tag"
   ```

2. Вносим минимальное исправление, проверяем, коммитим и отправляем рабочую ветку.
   Открываем PR: **base `main`, compare hotfix-ветка**.
3. После зелёных проверок сливаем через **Merge pull request**.
4. Создаём новый тег вида `hotfix-release-ГГГГ-ММ-ДД` или
   `hotfix-release-ГГГГ-ММ-ДД.N` и отправляем именно его.

   Перед командами ниже проверяем, что в `main` нет посторонних невыпущенных
   изменений. Если они есть, вместо `origin/main` выбираем **проверенный SHA
   исправления из hotfix-ветки**, который уже вошёл в историю `main` через merge
   commit. Не включаем в срочный выпуск неготовые функции из `main`.
   Подробности: [RELEASES.md](docs/RELEASES.md#hotfix).

   Для выпуска актуального `main`:

   ```bash
   git fetch origin main --tags
   release_day="$(date +%F)"
   hotfix_tag="hotfix-release-${release_day}.1"
   git ls-remote --tags origin "refs/tags/hotfix-release-${release_day}*"
   # Выберите свободное имя; если .1 занято, измените hotfix_tag.
   git tag -a "$hotfix_tag" origin/main -m "CRM hotfix ${hotfix_tag}"
   git push origin "refs/tags/${hotfix_tag}"
   ```

5. Проверяем успешный деплой и саму CRM. Возвращаем исправление в `develop`
   через PR; при изолированном hotfix с невыпущенными изменениями в `main`
   переносим именно исправление отдельной рабочей веткой от `develop`.

## Если выпуск упал

Не перемещаем тег, не отключаем проверки и не делаем прямой push в общие ветки.
При временном сбое повторяем **Re-run failed jobs**. Если нужен фикс кода,
проводим его через новый PR и выпускаем новый тег.

При ошибке переключения скрипт возвращает предыдущий gateway и фоновые процессы.
Миграции БД автоматически не откатываются. Новый код и миграции должны быть
совместимы с предыдущим API; состояние БД вручную не восстанавливаем без
отдельного плана. Запуск старого тега поверх нового production пайплайн запрещает.

Конфигурация и диагностика сервера: [CI/CD](docs/CI_CD.md).
Формат тегов и политика релизов: [RELEASES.md](docs/RELEASES.md).
