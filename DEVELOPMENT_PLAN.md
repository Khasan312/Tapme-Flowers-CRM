# Tapme Flowers — план первой рабочей версии

Дата: 21 сентября 2026 года.
Текущая точка продолжения на 22 сентября — [SESSION_HANDOFF.md](SESSION_HANDOFF.md).
Основа: `tapme-flowers-v1.html` и `TODO-v1.md`.
Согласовано: Python, Django REST Framework, разработка по модулям,
инверсия зависимостей и заменяемые реализации внешних компонентов,
запуск базы и брокеров через Docker Compose.
Решения ниже реализованы в коде; внешнее размещение и проверка пилотом остаются отдельным этапом.

Статус на 22 сентября 2026: этапы 1–4 реализованы — основа, полный путь заказа,
оплаты/фото, задания флориста и курьера, клиентские карточки, импорт/экспорт,
напоминания, отзывы/жалобы и настройки. Разделы интерфейса используют реальный API.
Из этапа 5 реализованы настройки первого запуска, смена/восстановление паролей,
мобильные экраны, показатели, серверная конфигурация HTTPS, резервирование и
проверка восстановления. Остаются фактическое размещение на выбранном сервере,
внешние копии/мониторинг и приёмка реальным магазином. Подробности и результаты
проверок — в SESSION_HANDOFF.md; команды размещения — docs/DEPLOYMENT.md.

Цель: магазин принимает заказ, передаёт флористу, фиксирует оплату и доставку,
сохраняет историю клиента и получает очередь напоминаний. Данные доступны
сотрудникам с разных устройств и сохраняются после перезапуска приложения.

## 1. Используемый стек

| Часть | Выбор | Назначение |
| --- | --- | --- |
| Бэкенд | Python 3.13, Django 5.2 LTS, Django REST Framework | Бизнес-правила, API, служебная админка |
| База | PostgreSQL | Постоянное хранение, ограничения и транзакции |
| Интерфейс | React, TypeScript, Vite | Постепенный перенос экранов существующего макета с сохранением дизайна |
| Авторизация | Django sessions, HttpOnly cookies, CSRF | Вход сотрудников в браузере; интерфейс и API на одном origin |
| Фоновые задачи | Celery, Redis, периодический планировщик | Периодическое обновление очереди напоминаний |
| Фото | Закрытый локальный том; заменяемый S3-адаптер | Фото букетов с контролем доступа; локальные файлы при разработке |
| Окружение | uv, Docker Compose | Зафиксированные зависимости и воспроизводимый запуск |
| Проверки | pytest, pytest-django, Ruff; Playwright для основных сценариев | Проверка прав, бизнес-правил и работы интерфейса с API |
| Контракт API | OpenAPI | Форматы запросов, ответов и ошибок для интерфейса |

Версии Python-зависимостей закреплены в backend/uv.lock, frontend — в package-lock.json.
Для первого размещения: Linux-сервер, reverse proxy с HTTPS, сервер Django,
PostgreSQL, резервные копии и сбор ошибок. Провайдера выбираем перед размещением.

Локальная инфраструктура описана в `compose.yaml`: PostgreSQL 17 запускается
по умолчанию, Redis 8.2 — через профиль `jobs`. Для обоих сервисов предусмотрены
проверки готовности, отдельные тома и публикация портов только на localhost.
Пример настроек — `.env.example`, команды запуска — в [README.md](README.md).
Gunicorn/Django включается профилем `app`; Redis, worker и beat — профилем `jobs`. Python-приложение также можно запускать
на компьютере разработчика.

## 2. Архитектура и модули

Один репозиторий: `backend/`, `frontend/`, `infra/`, `docs/`.
Один Django-проект с отдельными приложениями. Модули добавляются по этапам.

| Модуль | Ответственность |
| --- | --- |
| accounts | Пользователи, вход, восстановление доступа |
| businesses | Бизнес, магазин, членство сотрудников и роли, настройки |
| customers | Клиенты, получатели, адреса, заметки, важные даты и согласие на сообщения |
| catalog | Простой прайс товаров и услуг |
| orders | Заказы, состав, назначение флориста, статусы, фото, история изменений |
| payments | Ручной учёт оплат и возвратов по заказам |
| deliveries | Окна доставки, назначение курьера, результат доставки |
| reminders | Правила, шаблоны, очередь и история напоминаний |
| feedback | Отзывы, жалобы и задачи по их решению |

Импорт относится к customers, простые отчёты строятся на данных заказов и оплат.
Отдельные сервисы для каждого модуля на старте не нужны.

Основные связи: бизнес → магазин; пользователь ↔ бизнес через членство с ролью;
клиент → получатели и даты; заказ → клиент, снимок данных получателя, позиции,
оплаты, доставка, события и фото. Изменение прайса или адреса в карточке клиента
не должно переписывать старые заказы.

### Границы зависимостей — согласовано 21 сентября 2026

Применяем Dependency Inversion Principle: бизнес-правила и прикладные сценарии
определяют нужные им контракты. Реализации работы с базой, файлами и внешними
сервисами соответствуют этим контрактам и подключаются снаружи.

| Слой | Содержимое | Допустимые зависимости |
| --- | --- | --- |
| domain | Сущности, значения, правила статусов, сумм и оплат | Стандартная библиотека Python и собственные доменные типы |
| application | Сценарии, контракты зависимостей, команды и результаты | domain, собственные интерфейсы и публичные контракты модулей |
| infrastructure | Реализации репозиториев, транзакций, файлов и фоновых задач | Контракты application, domain, Django ORM и библиотеки провайдеров |
| api | DRF views/serializers, преобразование HTTP-запросов и ошибок | application, DRF, функции сборки зависимостей |

Контракты описываем через `typing.Protocol`; реализации передаём явно через
аргументы функций или конструкторы. Их выбор выполняется в одном месте сборки
приложения с использованием настроек. Отдельный DI-фреймворк на старте не нужен.
Протоколы задают форму интерфейсов; поведение подтверждают тесты контрактов.

Начальные границы, добавляемые по мере реализации сценариев:

- `OrderRepository` — получение и сохранение доменного заказа в контексте бизнеса.
  Первая постоянная реализация работает через Django ORM и PostgreSQL;
  реализация в памяти используется для тестов сценариев.
- `UnitOfWork` — единая граница транзакции для связанных изменений заказа,
  оплат и истории. Репозитории внутри неё используют одну транзакцию.
  Django-реализация управляет `transaction.atomic`, блокировками или проверками
  версии записи; конфликт преобразуется в ошибку прикладного уровня.
- `PhotoStorage` — сохранение, чтение и удаление фото по устойчивому ключу.
  Адаптер использует Django Storage, за которым выбирается локальный диск
  или S3-совместимый backend. В ядро не передаём SDK, bucket, FileField или
  адрес провайдера. Ссылки для просмотра выдаются после проверки доступа.
- Контракты чтения для списков и отчётов возвращают готовые данные с пагинацией.
  Конкретные SQL-запросы остаются в инфраструктуре.

Сущности и результаты на границах — обычные Python-типы и dataclass.
В domain/application не передаём Django Model, QuerySet, HTTP Request,
UploadedFile, Celery task или исключения драйвера базы. Django-модели и миграции
считаются деталями хранения; адаптеры преобразуют их в доменные объекты.
Контекст сотрудника и бизнеса передаётся явно, проверка полномочий выполняется
в прикладном сценарии. Это правило действует также для команд и фоновых задач.

Модули обращаются через публичные прикладные контракты. Прямое изменение
ORM-моделей соседнего модуля и циклические зависимости запрещены.
Изменения заказов и оплат через API, админку и фоновые задачи проходят
одни и те же сценарии. Стандартные механизмы Django auth остаются частью
инфраструктуры; ядро получает только нужные ему данные об исполнителе.

Контракт описывает также ошибки, изоляцию бизнеса, повторные запросы и
конкурентные изменения. Транзакция базы не охватывает файловое хранилище:
для загрузки фото предусматриваем очистку несвязанных файлов при сбоях.
Внешние действия запускаем после фиксации транзакции; для обязательной
доставки фоновой задачи используем запись задания в той же транзакции
с последующей обработкой и повторами.

Замена реализации сохраняет бизнес-логику при соблюдении того же контракта.
Перенос на другую СУБД всё равно требует миграции данных, адаптации запросов,
индексов, ограничений и проверки транзакций. Перенос фотографий требует
копирования файлов с сохранением ключей или их отображения. Эти операции
не сводятся к изменению одной настройки.

Выделяем интерфейсы на границах бизнес-сценариев и внешних зависимостей.
Универсальный CRUD-репозиторий для каждой таблицы и реализации для всех
возможных провайдеров заранее не создаём.

## 3. Правила, которые закладываем в фундамент

- Каждый бизнес видит только собственные данные. Это проверяется на сервере
  при чтении, поиске, изменении, экспорте и выполнении фоновых задач.
  Переданный браузером business_id сам по себе не даёт доступа.
- Роли привязаны к членству в бизнесе. Владелец управляет сотрудниками и настройками;
  менеджер — клиентами и заказами; флорист — доступными ему заданиями на сборку;
  курьер — назначенными доставками и необходимыми для них контактами.
- Для первой версии у бизнеса одна торговая точка. Модель магазина предусмотрена,
  полноценная работа сети точек отложена. По умолчанию KGS и Asia/Bishkek.
- Суммы рассчитывает сервер с точной десятичной арифметикой. Оплаты и возвраты
  хранятся отдельными записями; статус оплаты вычисляется по ним.
- Допустимые переходы статусов проверяет сервер. Назначения, изменения заказа
  и оплаты фиксируются в истории с сотрудником и временем. Одновременное взятие
  заказа двумя флористами разрешается атомарно.
- Создание заказа и запись оплаты защищены от повторной обработки одного запроса.
- Публичная страница заказа использует непредсказуемый отзываемый токен и выдаёт
  только предназначенные клиенту данные. Внутренние заметки туда не попадают.
- В первой версии WhatsApp открывается с подготовленным сообщением. Открытие ссылки
  не подтверждает отправку, доставку или ответ; сотрудник отдельно отмечает действие.
- Импорт не создаёт согласие на сообщения автоматически. Напоминания учитывают
  согласие, часовой пояс, паузу при жалобе и защиту от повторного создания задач.

## 4. Последовательность разработки

1. **Схема данных и правила — реализовано.** Описать доменные сущности, поля, связи, матрицу ролей,
   переходы статусов, контракты репозитория и транзакции, API первого сценария.
   Начальное допущение: владелец и менеджер работают
   в кабинете, флорист и курьер — через адаптированные экраны в браузере.
   Готово, когда понятно, кто какие данные читает и какие действия выполняет.

2. **Фундамент и первый сохранённый заказ — реализовано.** Реализовать сценарий создания заказа
   через интерфейсы и проверить бизнес-правила с реализациями в памяти.
   Создать backend/frontend, подключить адаптер Django ORM с PostgreSQL,
   настроить миграции, вход и выход, бизнес и сотрудников. Сделать
   API клиентов, простого прайса и создания/просмотра заказа. Подключить форму
   и список заказов из макета к API. Начальное создание бизнеса — через служебную
   команду или админку. Готово, когда заказ сохраняется после обновления страницы
   и перезапуска приложения, виден второму сотруднику своего бизнеса и недоступен
   сотруднику другого бизнеса. Это первый демонстрируемый результат.

3. **Весь путь заказа — реализовано.** Добавить редактирование, назначение флориста, фото сборки,
   статусы, отмену с причиной, частичные оплаты и возвраты, курьера, окна доставки,
   самовывоз и страницу статуса для клиента. Готово, когда заказ можно провести
   от приёма до вручения или отмены с корректной историей и суммами.

4. **Клиентская база и повторные продажи — реализовано.** Добавить карточки получателей и дат,
   импорт CSV/XLSX с предпросмотром и обработкой дублей внутри бизнеса, экспорт,
   очередь напоминаний, шаблоны, отметки сотрудника, отзывы и жалобы.
   Готово, когда реальная база импортируется с отчётом об ошибках, напоминания
   появляются по правилам, а жалоба приостанавливает обращения к клиенту.

5. **Подготовка пилота — код готов, внешнее размещение и приёмка впереди.** Завершить первый запуск магазина, восстановление доступа,
   пустые состояния, ошибки и мобильные сценарии. Добавить простые показатели:
   заказы, полученные оплаты, возвраты и своевременность доставки. Настроить HTTPS,
   хранение фото, резервное копирование с проверкой восстановления и мониторинг.
   Готово, когда пилотный магазин проходит основные сценарии на тестовом окружении
   и можно подключить второй независимый бизнес без изменения кода.

Делаем API и соответствующий экран вместе на каждом этапе. Интерфейс последовательно
получает реальные данные; исходный HTML остаётся ориентиром для дизайна.

## 5. Проверки перед пилотом

- Тесты доменных правил и прикладных сценариев без Django, базы и облачного хранилища.
- Проверка импортов между слоями и модулями, статическая проверка типов контрактов.
- Общие тесты контрактов для заменяемых реализаций; отдельные интеграционные тесты
  на PostgreSQL для транзакций, ограничений и одновременных действий сотрудников.
- Автотесты изоляции двух бизнесов, в том числе подстановка чужого ID в связи,
  доступ к файлам, поиску, отчётам и фоновой обработке.
- Проверки матрицы ролей, конфликтующих действий сотрудников, частичных оплат,
  возвратов и повторных запросов.
- Проверки повторного запуска фоновых задач, правил напоминаний и импорта дублей.
- Основные сценарии в браузере: вход → создание заказа → сборка → доставка;
  отдельно самовывоз, отмена и ошибка сохранения.
- Проверка восстановления базы и фотографий из резервной копии.

## 6. После первой версии

Склад, партии и списания, себестоимость и прибыль, кассовые интеграции,
бонусы, автоматические сообщения WhatsApp Business API, API служб доставки,
онлайн-витрина, сеть торговых точек, автоматическая оплата подписки магазинами.
Учёт оплаты заказа в первой версии не является интеграцией с платёжной системой.

Общие процессы используем как основу продукта; отличия магазинов в окнах доставки,
прайсе, сотрудниках и шаблонах выносим в настройки и проверяем на пилоте.
Сроки оцениваем после описания моделей и первого рабочего сценария.
