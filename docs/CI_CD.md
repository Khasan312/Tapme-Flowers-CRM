# Автоматическое обновление Tapme

Workflow `.github/workflows/production.yml` проверяет PR и push в `develop` и
`main`. Сервер обновляется после публикации GitHub Release с тегом
`release-ГГГГ-ММ-ДД` или `hotfix-release-ГГГГ-ММ-ДД[.N]`. Workflow проверяет тег
и историю, запускает тесты, собирает API и frontend в GitHub-hosted runner,
публикует образы с тегом полного SHA в приватный GitHub Container Registry
и передаёт деплой серверному агенту. Обычный merge и **Run workflow** прод не меняют.

Порядок работы с `develop`, `main`, тегами и hotfix: [RELEASES.md](RELEASES.md).

Сам сервер не собирает образы. Для запуска он использует краткоживущий
`GITHUB_TOKEN` с правом чтения пакетов; SSH-ключ владельца в GitHub не передаётся.
Временный Docker login удаляется после завершения, включая ошибку.

## Подготовленный сервер

- Ubuntu, Docker Engine и Compose v2, 4 ГБ RAM / 2 vCPU.
- Пользователь `deploy` с доступом к Docker.
- GitHub Actions Runner: `/opt/tapme-runner`, служба от `deploy`.
- Runner подключён только к приватному `Khasan312/Tapme-Flowers-CRM`, метки:
  `self-hosted`, `linux`, `x64`, `production`.
- `/srv/tapme/.env.production` принадлежит `deploy`, права `600`.

Пользователь с доступом к Docker и workflow, запущенный на таком агенте, имеют
широкие права на сервер. PR проверяются на GitHub-hosted runner; серверный job
доступен только workflow на `main`. Изменения workflow требуют такого же
контроля, как изменения серверных настроек.

Настройки окружения соответствуют `.env.production.example`. Обязательны
`PUBLIC_DOMAIN`, `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`,
`DJANGO_SECRET_KEY`, `TAPME_BOOTSTRAP_PASSWORD`; секреты не помещают в Git.
Сохраняйте этот файл в защищённом месте: смена ключа Django завершает сессии,
а смена пароля PostgreSQL в файле не меняет пароль существующей БД.

## Первый запуск — выполняет владелец

После успешных проверок и слияния CI/CD в `main`, под `deploy` на сервере:

```bash
test "$(whoami)" = deploy
test -r /srv/tapme/.env.production
touch /srv/tapme/.deploy-enabled
```

Затем GitHub → **Releases → Draft a new release**: создать тег на `main`,
например `release-2026-10-18`, и нажать **Publish release**. При отсутствии
`.deploy-enabled` серверный job завершается ошибкой и не меняет рабочие
контейнеры. Само создание файла не запускает workflow. Черновик и pre-release
не обновляют прод.

На первом запуске скрипт создаёт постоянную БД, применяет миграции, собирает
статику и создаёт магазин `Tapme Flowers` с логином `owner`. Пароль находится
в `TAPME_BOOTSTRAP_PASSWORD` на сервере. Команда создания магазина идемпотентна:
при последующих деплоях существующий пароль не меняется. Локальная база,
пользовательские фотографии и незакоммиченный код с компьютера не переносятся.

## DNS и HTTPS

Для этого сервера: `95.216.171.101`, домен: `tapme.kg`.
На момент подготовки домен делегирован `duke.ns.cloudflare.com` и
`lisa.ns.cloudflare.com`. DNS-записи редактируют в обслуживающем домен аккаунте
Cloudflare; сайт `cctld.kg` является регистратором.

Добавьте записи, сохранив существующие MX/TXT и прочие записи:

| Тип | Имя | Значение |
| --- | --- | --- |
| A | @ | 95.216.171.101 |
| CNAME | www | tapme.kg |

Для первого выпуска сертификатов используйте **DNS only** и проверьте, что
порты 80/443 доступны извне. AAAA должна указывать на настроенный IPv6 сервера;
не добавляйте случайный IPv6. Если нет доступа к текущему Cloudflare, сначала
восстановите доступ либо согласованно перенесите DNS через регистратора.

Caddy получает сертификаты автоматически после распространения правильных
записей. До этого приложение можно проверить на самом сервере:

```bash
curl --fail -H 'Host: tapme.kg' http://127.0.0.1:8080/health/
```

Ожидается `{"status":"ok"}`. Это проверка приложения через gateway, а не
подтверждение готовности публичного HTTPS. Порт 8080 доступен только локально.

## Что происходит при обновлении

1. `flock` запрещает одновременные деплои. Образы выбираются по точному SHA.
   Релиз должен входить в историю `main` и сохранять уже развёрнутые коммиты.
2. PostgreSQL и Redis остаются постоянными, их порты не публикуются.
3. Перед миграцией создаётся `pg_dump -Fc` в `/srv/tapme/backups`.
   Ошибка или пустой файл останавливает деплой до миграции.
4. В неактивном слоте `blue`/`green` применяются миграции и запускается новая
   API/frontend-пара. Docker healthchecks проверяют доступность API и БД.
5. Старые Celery worker/beat останавливаются штатно; запускаются новые.
   Одновременно два планировщика beat не работают. Очередь хранится в Redis.
6. Gateway перечитывает конфигурацию Caddy без пересоздания контейнера.
   Дополнительно проверяются `/health/` и главная страница через gateway.
7. Только после успеха записывается `/srv/tapme/state/current`, затем сохраняется
   имя релиза в `/srv/tapme/state/release`.
   Старые API/frontend остаются запущены, старые фоновые процессы остановлены.

Хешированные frontend-ресурсы дополняются в общем томе: открытая перед
переключением страница продолжает загружать файлы своей версии. База, фото,
Redis, сертификаты и расписание Celery находятся в постоянных томах.

При ошибке до переключения трафик остаётся на прежней версии. При ошибке
переключения или финальной проверки скрипт возвращает предыдущую конфигурацию
gateway и фоновые процессы. Старые API/frontend сохраняются для восстановления.

**Граница автоматического отката:** применённые миграции БД не отменяются.
Для обновления без простоя миграции обязаны быть совместимы с обеими версиями
кода: сначала добавление новых полей/таблиц, удаление старых отдельным релизом.
Несовместимое изменение схемы требует отдельного плана обслуживания.

## Управление и диагностика

GitHub Actions показывает ход проверок, сборки и деплоя. На сервере:

```bash
cat /srv/tapme/state/current
cat /srv/tapme/state/release
docker ps
df -h /
```

Файл состояния содержит цвет и SHA последнего успешного деплоя.
Для временного выключения будущих деплоев:

```bash
rm /srv/tapme/.deploy-enabled
```

Работающий сайт продолжает обслуживать запросы. Включение — повторный `touch`.
Не используйте `docker compose down -v`: это не способ обновления приложения.

Копия перед миграцией содержит БД, но не отдельную копию фотографий. Полное
резервирование, проверка восстановления и копии вне сервера описаны в
[DEPLOYMENT.md](DEPLOYMENT.md). Автоматическое внешнее резервирование и
уведомления мониторинга этим workflow не настраиваются. Релизы, образы,
хешированные ресурсы и дампы сохраняются; контролируйте свободное место и
настройте срок хранения перед эксплуатацией с реальными данными.
