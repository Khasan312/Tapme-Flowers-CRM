# Ветки, релизы и срочные исправления

Пошаговая инструкция для участников команды, включая первый clone, рабочие
ветки и PR: [CONTRIBUTING.md](../CONTRIBUTING.md).

Источником продовых версий служит `main`; отдельная ветка `release` не нужна.
Разработка идёт через рабочие ветки от `develop`. Обновление сервера
запускается после отправки нового релизного тега на коммит, уже вошедший в `main`.
Обычный merge и push ветки сами по себе прод не обновляют.
Дата в теге обозначает версию; она не задаёт время будущего запуска.

Изменения в `develop` входят через PR из рабочих веток, созданных от `develop`:
`feature/<задача>` → PR → проверки → merge в `develop`. Прямые push в `develop`
и `main` запрещены локальным хуком; серверное ограничение ожидает GitHub Pro.

| Действие | Результат |
| --- | --- |
| PR в `develop` или `main` | Тесты, проверки, сборка API и сайта |
| Push в `develop` | Тесты, сборка и обновление отдельного тестового стенда |
| Push в `main` | Тесты, проверки и сборка без деплоя |
| Actions → Run workflow | Только проверки и сборка |
| Push нового `release-*` или `hotfix-release-*` тега | Проверка тега и истории, тесты, сборка, публикация образов, деплой |
| Изменение или удаление тега | Деплой отклоняется |
| GitHub Release для существующего тега | Дополнительный деплой не запускается |

Конфигурация тестового ноутбука, его данные и HTTPS: [STAGING.md](STAGING.md).

## Плановый выпуск

1. Создать `feature/<задача>` от `develop`, внести изменения и открыть PR в `develop`.
2. Когда версия готова, открыть PR `develop` → `main` и дождаться зелёных проверок.
3. Выполнить **Merge pull request**. Merge commit сохраняет историю обеих веток;
   squash для регулярного объединения `develop` и `main` не использовать.
4. Создать тег на актуальном коммите `main` и отправить его в GitHub:

   ```bash
   git fetch origin main
   git tag -a release-2026-10-18 origin/main -m "Release 2026-10-18"
   git push origin refs/tags/release-2026-10-18
   ```

   Локальное создание тега не запускает Actions: запуск происходит на `git push`.
   Тег на `origin/main` не включает незакоммиченные файлы с компьютера.
5. Дождаться зелёного **Deploy production** в Actions. Создание тега само по себе
   ещё не означает успешный деплой: проверки и сборка должны завершиться.
6. Синхронизировать `main` обратно в `develop` через PR с merge commit,
   особенно если в `main` отдельно входили hotfix или служебные изменения.

## Hotfix

Срочный выпуск проходит проверки и PR, но не ждёт готовности `develop`.

1. Создать `hotfix/<ошибка>` от текущей продовой версии. Если `main` соответствует
   проду — от `main`; иначе от последнего успешно развёрнутого релизного тега.
2. Внести минимальное исправление и открыть PR в `main`.
3. После успешных проверок выполнить **Merge pull request**.
4. Создать и отправить тег исправления:

   ```bash
   git fetch origin main
   git tag -a hotfix-release-2026-10-18.1 origin/main -m "Hotfix 2026-10-18.1"
   git push origin refs/tags/hotfix-release-2026-10-18.1
   ```

   Если в `main` уже есть другие невыпущенные изменения, вместо `origin/main`
   указать SHA исправленного коммита из hotfix-ветки. Коммит обязан быть предком
   `main`; для этого
   PR hotfix нужно объединять merge commit, а не squash/rebase. Так на прод
   попадёт исправление без невыпущенных изменений `main`.
5. Дождаться успешного деплоя и перенести исправление в `develop` через PR.

## Имена и неизменяемость тегов

- Плановый: `release-ГГГГ-ММ-ДД`.
- Срочный: `hotfix-release-ГГГГ-ММ-ДД` или `hotfix-release-ГГГГ-ММ-ДД.N`.
- Повторный выпуск за день: суффиксы `.1`, `.2`, `.3`; они допустимы и для
  плановых релизов. Дата должна существовать, номер должен быть положительным.
- `*` — обозначение произвольного продолжения в обсуждении, не символ имени тега.
- Новую версию выпускают новым тегом. Пайплайн не обновляет прод по изменённым
  или удалённым тегам. Для тегов без GitHub Release серверные правила GitHub
  пока недоступны из-за тарифа, поэтому сам Git не запрещает передвинуть тег.
- При желании можно [добавить описание релиза](https://github.com/Khasan312/Tapme-Flowers-CRM/releases/new)
  в GitHub, выбрав уже отправленный тег. Это необязательный шаг без повторного
  деплоя. Неизменяемость опубликованных GitHub Releases включена и защищает
  связанные с ними теги и вложения.
- Тег обязан указывать на коммит, уже вошедший в `main`. На сервере дополнительно
  проверяется, что выпуск сохраняет историю текущей продовой версии.

При временной ошибке можно повторить тот же запуск через **Re-run failed jobs**.
Для исправления кода нужен новый коммит и новый тег. Откат схемы БД не выполняется
автоматически; восстанавливать старый тег поверх нового прода пайплайн запрещает.

## Защита main и develop

Желаемые правила хранятся в `infra/github/main-protection.json` и
`infra/github/develop-protection.json`: только PR,
обязательные `Tests and checks`, `Build api image`, `Build web image`, актуальная
база PR, закрытые обсуждения; force push и удаление запрещены. Правило применяется
и к администратору. Чужое одобрение не обязательно, чтобы владелец мог работать
один; при появлении команды число approvals можно увеличить.

На момент настройки GitHub ответил `403` и потребовал GitHub Pro для защиты
приватного репозитория. Серверная защита **не включена**. После подключения
подходящего тарифа выполнить на компьютере с авторизованным `gh`:

```bash
bash infra/github/apply-branch-protection.sh
```

Приватность репозитория этот скрипт не меняет. Установленный в общей `.git/hooks`
локальный `pre-push` блокирует случайный push в `main` и `develop` с этого компьютера.
Это локальная мера: она обходится и не заменяет запрет на стороне GitHub.
Версия хука хранится в `.githooks/pre-push`; на других компьютерах его нужно
установить отдельно, сохранив собственные хуки, если они уже есть.

## Проверка версии на сервере

```bash
cat /srv/tapme/state/current
cat /srv/tapme/state/release
curl --fail --max-time 10 -H 'Host: tapme.kg' http://127.0.0.1:8080/health/
```

`current` содержит слот и SHA последнего успешного деплоя; `release` — тег и SHA.
Файл `release` появится после первого успешного выпуска по новой схеме. Подробности
обновления без перезагрузки сервера и ограничений миграций: [CI/CD](CI_CD.md).
