# Тестовый Flower CRM из develop

Стенд на отдельном Ubuntu-ноутбуке обновляется только после push в `develop`
(включая merge PR), успешных проверок и публикации обоих Docker-образов.
PR, `main`, релизные теги и ручной Run workflow этот стенд не обновляют.
Production по-прежнему обновляется только по релизным тегам.

На ноутбуке работает отдельный GitHub Actions runner с меткой `flower-staging`,
подключённый только к приватному `Khasan312/Tapme-Flowers-CRM`.
Проверки и сборка выполняются на GitHub-hosted runner. Серверный job получает
короткоживущий `GITHUB_TOKEN` для скачивания образов по полному SHA коммита.
Доступ к Docker даёт серверному runner широкие права на этот ноутбук;
доверять изменениям workflow следует как изменениям серверных настроек.

Runner можно установить в `~/apps/flower-crm-staging/runner` от пользователя
с доступом к Docker. На ноутбуке без отдельной systemd-службы запускать
`bash ~/apps/flower-crm-staging/infra/staging/start-runner.sh` при загрузке и
раз в минуту через пользовательский cron. Скрипт использует `flock`: повторные
вызовы не запускают второй runner. Cron должен быть включён как системная
служба. stdout/stderr runner направляются в `state/runner.log`.
Настройки сна и закрытия крышки Ubuntu настраиваются отдельно от контейнеров.

## Каталоги и первый запуск

По умолчанию корень стенда — `$HOME/apps/flower-crm-staging` пользователя runner.
Другой путь задаётся через `TAPME_STAGING_ROOT`. Файл `.env.staging` создаётся
из `infra/staging/env.example` с новыми секретами и правами `600`.
Не копируйте production `.env`, базу, медиа или ключи интеграций.

После подготовки окружения включите деплой файлом `.deploy-enabled` в корне
стенда. Первый запуск применяет миграции и создаёт бизнес
«Flower CRM — тестовый стенд», логин `owner`, пароль из
`TAPME_BOOTSTRAP_PASSWORD`. Повторный деплой пароль не меняет.

`infra/staging/deploy.sh FULL_SHA` обычно запускается workflow. Для первой
локальной сборки уже имеющегося коммита `develop` можно использовать собственный
префикс образов и `TAPME_STAGING_LOCAL_IMAGES=true`; скрипт проверит наличие
обоих образов вместо доступа к registry. Эти параметры не нужны в CI.

Compose-проект `flower-crm-staging` имеет собственные PostgreSQL, Redis, фото,
статику, frontend-ресурсы и расписание Celery. Порты базы и Redis не публикуются.
Логи ограничены тремя файлами по 10 МБ на контейнер. Docker должен запускаться
при загрузке ОС; контейнеры используют `restart: unless-stopped`.

## HTTPS и Cloudflare

Веб-сервис слушает только `127.0.0.1:8090` и Docker-сеть
`flower-crm-staging_edge`. Подключите Cloudflare Tunnel к `http://web:80`
в этой сети либо к `http://127.0.0.1:8090` при запуске cloudflared на хосте.
В `.env.staging` задайте точный публичный HTTPS-хост в `PUBLIC_DOMAIN`.
После смены адреса пересоздайте API, web, worker и beat с тем же SHA и
префиксом образов. HTTPS завершается в туннеле; Caddy передаёт Django
фиксированный доверенный Host и HTTPS-протокол. Обход туннеля из LAN закрыт
привязкой опубликованного порта к localhost.

Для постоянного адреса требуется именованный туннель и домен, DNS которого
управляется в Cloudflare. Временная ссылка Quick Tunnel живёт только пока
работает его процесс; при новом запуске адрес изменяется. После изменения
нужно обновить `PUBLIC_DOMAIN`. Она подходит для первой проверки, но не
заменяет постоянный адрес для команды и webhook.

Реальные сообщения Meta и внешние AI-запросы в этой конфигурации отключены.
DEBUG выключен, HTTPS-cookie включены. Локальный симулятор сообщений,
которому нужен DEBUG, здесь недоступен. Поисковикам отправляется `noindex`.
Доступ к CRM требует входа; noindex не является контролем доступа.

## Обновление и восстановление

Скрипт блокирует параллельные деплои, проверяет конфигурацию, скачивает образы
и создаёт `pg_dump` до остановки приложения. Затем останавливает API и фоновые
задачи, применяет миграции и запускает новую версию. Для стенда допустима
короткая недоступность во время обновления.

`state/current` содержит SHA последнего успешного деплоя,
`state/previous` — предыдущий, `state/image-prefix` — префикс образов.
Файлы конкретного запуска находятся в `releases/SHA/staging/`.
Номер версии также доступен в заголовке HTTP `X-Flower-Revision`.

При ошибке скачивания или резервного копирования старая версия продолжает
работать. При ошибке миграции или запуска стенд может остаться остановленным;
последний успешный SHA и резервная копия сохраняются. Автоматического отката
схемы или данных нет. Восстановление выполняется отдельно после анализа ошибки.
Ни одна команда деплоя не удаляет Docker-тома.

Резервные копии, образы и исходники накапливаются. Контролируйте свободное место
и удаляйте только выбранные старые артефакты этого стенда. Глобальный Docker
prune на ноутбуке с другими проектами не используется.

Проверки настройки: `python3 -m unittest discover -s infra/staging/tests -v`,
`bash -n infra/staging/deploy.sh`, `shellcheck infra/staging/deploy.sh`,
Compose config и Caddy validate с тестовым окружением. Для готового стенда
проверяются `/health/`, frontend, вход/CSRF и фоновые задачи.
