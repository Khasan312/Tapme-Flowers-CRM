# 02. Уведомления: звук, push на телефон, Telegram, поток событий

Решение: D-10. Макеты: `design-crm/png/4-mobile.png` (push), `design-onboarding/png/2-channels.png`
(карточка «Уведомления о чатах»), `design-onboarding/png/4-first-login.png` (разрешение push).

## 1. Цель

Сотрудник узнаёт о важном событии за секунды — даже если вкладка CRM закрыта или
телефон в кармане. Чаты и проверка оплаты держатся на этом: без уведомлений клиент
ждёт, и смысл канала теряется.

## 2. Новый модуль `notifications`

Слои как в остальных модулях: доменные правила (кому и когда), сценарии, адаптеры
доставки (поток в браузер, Web Push, Telegram).

### 2.1. События

| Код события | Когда возникает | Кому | Звук | Push | Telegram-дубль |
| --- | --- | --- | --- | --- | --- |
| `chat.handoff` | Клиент нажал «Позвать менеджера» или бот не понял дважды | ответственный; если нет — менеджеры точки разговора; если точки нет — все менеджеры | да | да | да, если нет ответа N минут |
| `chat.message` | Новое входящее в разговоре в режиме «человек» | ответственный (или как выше) | да | да | нет |
| `chat.waiting` | Клиент ждёт ответа дольше порога (по умолчанию 5 мин) в рабочие часы | ответственный + менеджеры точки | повтор | да | да, если ждёт дольше второго порога (10 мин) |
| `payment.receipt` | Клиент прислал чек к заказу `pending` | ответственный + менеджеры точки заказа | да | да | нет |
| `order.bot_created` | Бот создал заказ `pending` | менеджеры точки | да | да | нет |
| `order.confirmed` | Заказ подтверждён и стал `new` | флористы точки (свободный заказ) или назначенный флорист | да | да | нет |
| `order.assigned` | Сотруднику назначили заказ или доставку | этот сотрудник | да | да | нет |
| `order.changed` | Изменились время, адрес или состав принятого в работу заказа | назначенные флорист и курьер | да | да | нет |
| `bouquets.missing` | К 10:00 у точки нет ни одного букета дня (P1) | флористы точки | нет | да | нет |
| `channel.alert` | Ухудшилось качество номера, отклонён шаблон, отключился канал, ошибки отправки | владелец | нет | да | да |
| `reminders.ready` | Утренняя очередь напоминаний готова (P1) | менеджеры точки | нет | да (в 9:00 или начало смены) | нет |

### 2.2. Хранение

`notifications.NotificationRecord`:

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | UUID | |
| `business` | FK | изоляция |
| `user` | FK | получатель |
| `kind` | str(40) | код события |
| `title`, `body` | str | короткий текст для показа и push (без лишних персональных данных) |
| `link` | str | путь в CRM: `/?view=chats&conversation=…` |
| `dedupe_key` | str(200) | одно событие → одно уведомление на пользователя; уникальная пара `user, dedupe_key` |
| `created_at`, `read_at` | datetime | |
| `delivered` | JSON | `{"stream": "…", "push": "…", "telegram": "…"}` — время и результат по каналам |

`notifications.PushSubscription`: `user, endpoint, p256dh, auth, user_agent, created_at, last_ok_at, failed_count`.
Подписка удаляется после ответа сервиса push 404/410.

`notifications.UserPreference`: `user, sound_enabled (true), push_enabled, quiet_from, quiet_to,
telegram_chat_id, telegram_linked_at, muted_kinds (список)`.

## 3. Поток событий в браузер (реальное время)

- **FR-NT-010 (P0).** Эндпоинт `GET /api/v1/stream/` (Server-Sent Events) для
  вошедшего пользователя. Передаёт события: `notification`, `chat.message`,
  `chat.updated`, `order.updated`, `draft.updated`, `reminder.updated`. Формат —
  JSON с `type`, `business_id`, идентификаторами и минимальными полями для
  обновления интерфейса; полные данные интерфейс получает обычным API.
  - Работает под ASGI (Uvicorn worker в Gunicorn или отдельный ASGI-процесс);
    WSGI-воркеры не держат долгие соединения (см. NFR-IN-002).
  - Источник — Redis pub/sub, канал на пользователя и на компанию.
  - Каждые 25 секунд — комментарий-пинг; при разрыве браузер переподключается с
    `Last-Event-ID`; сервер досылает пропущенные события за последние 5 минут из
    короткого журнала в Redis. Если ID старше журнала или журнал потерян, сервер
    передаёт `resync_required`; интерфейс заново получает доступные данные и счётчики
    через API без очистки черновиков. Обычное переподключение не считается гарантией
    полноты истории после долгого отсутствия.
  - Пользователь получает события только своих компаний и точек (проверка при
    подписке и при отправке).
  - Критерий: сообщение клиента появляется в открытом чате менеджера не позже
    3 секунд после получения вебхука в 95 % случаев на тестовом стенде.
- **FR-NT-011 (P0).** Если поток недоступен (прокси режет SSE, ошибка 3 раза
  подряд), интерфейс переходит на опрос раз в 5 секунд для открытого чата и раз в
  20 секунд для счётчиков и показывает тонкую плашку «Связь восстанавливается».

## 4. Звук и уведомления в открытой CRM

- **FR-NT-020 (P0). Звук.** При событиях со звуком (таблица 2.1) CRM проигрывает
  короткий звук и показывает всплывающее уведомление внизу справа с кнопкой перехода.
  - Браузер не даёт играть звук до первого действия пользователя. После входа
    CRM показывает кнопку «Включить звук» в шапке, пока звук не разрешён; после
    первого нажатия в любом месте страницы звук считается разрешённым.
  - Разные звуки: новый чат/handoff, чек оплаты, новый заказ.
  - Звук не повторяется чаще одного раза в 3 секунды; пачка из 5 сообщений — один звук.
  - Если вкладка неактивна — в заголовке вкладки мигает счётчик «(3) Tapme».
  - Настройка «Звук в CRM» на пользователя (Профиль) и по умолчанию в «Каналах».
- **FR-NT-021 (P0). Счётчики.** В боковом меню у «Чатов» — число разговоров,
  ждущих ответа (не непрочитанных сообщений); у «Заказов» — число заказов `pending`
  своей точки. Обновляются из потока событий.
- **FR-NT-022 (P0). Центр уведомлений** (колокольчик в шапке): последние 50
  уведомлений, отметка «прочитано» по клику и «Прочитать все».

## 5. Push на телефон (PWA и Web Push)

- **FR-NT-030 (P0). Приложение на экран «Домой».** Фронтенд — устанавливаемое
  веб-приложение: `manifest.webmanifest` (название «Tapme», иконки 192/512,
  `display: standalone`, цвет темы `#0F2A22`), сервис-воркер (кэш оболочки,
  обработка push и кликов). Работает на iPhone (iOS 16.4+ после добавления на экран
  «Домой») и Android (Chrome).
- **FR-NT-031 (P0). Подписка.** Разрешение на уведомления запрашивается только по
  нажатию кнопки (экран первого входа или Профиль), никогда при загрузке страницы.
  После разрешения создаётся `PushSubscription` (VAPID-ключи в переменных окружения).
  На одного пользователя — несколько устройств.
- **FR-NT-032 (P0). Отправка.** Push отправляется фоновой задачей Celery (очередь
  `notifications`) не позже 2 секунд после события. Текст push не содержит
  телефон клиента и сумму: «Клиент зовёт менеджера», «Пришёл чек по заказу №67»,
  «Новый заказ на сборку №67». Нажатие открывает нужный экран CRM.
- **FR-NT-033 (P0). Тихие часы сотрудника.** В заданный сотрудником интервал push
  не отправляются, кроме `order.changed` для заказа, назначенного на ближайшие 2 часа.
- **FR-NT-034 (P0). Проверка.** В Профиле — «Отправить тестовое уведомление».
  В «Готовности команды» видно, у кого есть активная подписка (последняя успешная
  доставка за 7 дней).

## 6. Telegram-дубль

- **FR-NT-040 (P1). Привязка.** Сотрудник в Профиле нажимает «Подключить Telegram»
  → открывается бот Tapme с одноразовым кодом (`/start <код>`, срок 15 минут) →
  `telegram_chat_id` сохраняется. Один бот Tapme на все компании; токен бота в
  переменных окружения.
- **FR-NT-041 (P1). Эскалация.** Задача Celery beat раз в минуту ищет разговоры в
  режиме «человек», где последнее входящее старше порога (по умолчанию 10 минут)
  и нет ответа, в рабочие часы точки. Отправляет в Telegram ответственному (или
  менеджерам точки) одно сообщение на разговор за период ожидания: «Клиент ждёт
  ответа 10 минут. Открыть: <ссылка>». Без текста переписки.
- **FR-NT-042 (P1). Предупреждения владельцу** (`channel.alert`) дублируются в Telegram.

## 7. Настройки компании (Настройки → Каналы → «Уведомления о чатах»)

- Звук в CRM по умолчанию: вкл/выкл.
- Повторить звук, если клиент ждёт дольше: N минут (по умолчанию 5).
- Написать в Telegram, если нет ответа за: N минут (по умолчанию 10) — кому:
  ответственному / всем менеджерам точки.
- Список «Кто без push» — сотрудники без активной подписки.

## 8. Граничные случаи

- Сотрудник вошёл с трёх устройств — push на все три; прочтение на одном снимает
  счётчик на всех (через поток событий).
- Ответственный в отпуске/удалён — уведомления идут менеджерам точки.
- Ночь, рабочие часы точки закончились — `chat.waiting` и Telegram-эскалация не
  срабатывают; утром в начале смены — одно сводное уведомление «Ночью написали 4 клиента».
- iPhone без установки на экран «Домой» не получает push — экран первого входа
  объясняет это и проверяет `display-mode: standalone`.

## 9. Тесты

- Доменные: выбор получателей для каждого события (ответственный, точка, нет точки,
  удалённый ответственный), правила тихих часов и рабочих часов, дедупликация.
- Интеграционные: SSE получает событие своей компании и не получает чужой;
  переподключение с `Last-Event-ID` досылает пропущенное.
- Web Push: отправка через тестовый двойник, удаление подписки при 410.
- Playwright: входящее сообщение (через тестовый вебхук) → звук-заглушка вызван,
  счётчик «Чаты» увеличился, всплывающее уведомление ведёт в разговор.
