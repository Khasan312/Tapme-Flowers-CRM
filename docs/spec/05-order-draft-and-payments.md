# 05. Черновик заказа из переписки, подтверждение и оплата по QR

Решения: D-06, D-08, D-09, D-22. Макеты: `design-crm/png/1-chats.png` (правая
панель «Черновик заказа»), `design-crm/png/4-mobile.png` (черновик на телефоне).

## 1. Цель

Менеджер не переписывает заказ из чата руками: пока идёт переписка, справа
собирается черновик (букет, повод, когда, адрес, получатель, открытка). Менеджер
проверяет, правит и одной кнопкой создаёт заказ и отправляет QR. Чек клиента сам
прикрепляется к заказу, менеджер сверяет оплату, после чего заказ уходит флористу.

## 2. Новый статус заказа `pending` «Ждёт подтверждения»

Текущий путь статусов: `new → work → ready → route → done`, самовывоз `ready → done`,
отмена с причиной. Добавляется начальный статус:

```text
pending ──подтвердить──▶ new ──▶ work ──▶ ready ──▶ route ──▶ done
   │                                         └──(самовывоз)──▶ done
   └──отменить / истёк срок оплаты──▶ cancelled
```

- **FR-OD-001 (P0).** Заказ, созданный из черновика или ботом, получает `pending`, если
  требуется предоплата и она не внесена; иначе сразу `new`. Заказ, созданный менеджером
  в обычной форме, по-прежнему сразу `new` (поведение не меняется).
- **FR-OD-002 (P0).** Заказы `pending` не видны флористу и курьеру ни в одном списке,
  не считаются в «ждут сборки», выручке, опозданиях и вместимости курьеров, **но**
  занимают место в окне доставки (чтобы бот не продал окно дважды) и держат бронь букета дня.
- **FR-OD-003 (P0).** «Подтвердить» (`pending → new`) доступно владельцу и менеджеру точки.
  Если внесённая оплата меньше требуемой предоплаты, кнопка спрашивает «Оплата не
  внесена полностью. Подтвердить без предоплаты?» с обязательной причиной (событие в истории).
- **FR-OD-004 (P0).** `payment_due_at` сохраняется при создании `pending`:
  минимум из «сейчас + N минут» (по умолчанию 60) и «начало получения минус
  минимальное время на сборку точки» (по умолчанию 2 часа, Q-05).
  Если этот срок уже наступил, бот не создаёт истёкший заказ, а передаёт менеджеру.
  Менеджер для срочного заказа явно задаёт будущий срок до начала получения либо
  подтверждает без предоплаты с причиной (FR-OD-003). Обычная форма заказа остаётся
  без изменений. Продление «+30 мин» проверяет те же границы.
- По истечении срока автоматическая отмена возможна только при нулевой оплате
  и отсутствии чека на проверке: `cancelled`, причина «Не оплачен вовремя»,
  освобождение окна и букета, сообщение клиенту по правилам канала.
  При частичной оплате или непроверенном чеке заказ и бронь сохраняются,
  менеджер получает задачу принять решение; по таймеру деньги не возвращаются
  и букет не продаётся повторно. Подтверждение, отмена и таймер используют
  одну блокировку заказа и букета.
- **FR-OD-005 (P0).** На доске и в списке заказов у менеджера и владельца — вкладка
  или фильтр «Ждут подтверждения N» и бейдж в меню «Заказы».

## 3. Модель черновика (`orders.OrderDraft`, новая)

| Поле | Описание |
| --- | --- |
| `id` | UUID |
| `business`, `conversation`, `customer`, `point` | `point` пусто, пока не выбрана |
| `status` | `active` \| `converted` \| `abandoned` |
| `fields` | JSON (схема ниже) |
| `field_meta` | JSON: для каждого поля `source` (`ai`/`staff`/`bot`), `message_id` источника, `locked` (правил человек), `needs_check` (ИИ не уверен или данных не хватает) |
| `reference_photo_ids` | Фото-референсы из чата |
| `order` | FK на созданный заказ |
| `version` | Конкурентные правки |
| `ai_updated_at`, `updated_at`, `created_at` | |

Схема `fields`:

```json
{
  "items": [
    {"kind": "bouquet_of_day", "bouquet_id": "uuid", "title": "Пионы ×11", "price": "4800.00"},
    {"kind": "product", "product_id": "uuid", "name": "Открытка", "quantity": 1, "price": "100.00"},
    {"kind": "budget", "amount": "5000.00", "description": "пионы, без лилий"}
  ],
  "occasion": "День рождения мамы",
  "fulfillment": "courier | pickup",
  "date": "2026-10-18",
  "window": {"start": "09:00", "end": "11:00"},
  "requested_time_text": "к 10 утра",
  "zone_id": "uuid",
  "address": "ул. Токтогула, 125",
  "address_details": "кв. 12, домофон 12К",
  "location": {"lat": 42.87, "lng": 74.59},
  "recipient_name": "мама Айжан",
  "recipient_phone": "+996555…",
  "card_text": "С днём рождения!",
  "notes": "без лилий",
  "customer_name": "Алина"
}
```

Один активный черновик на разговор. Черновик без активности 72 часа → `abandoned`
(виден в карточке, можно восстановить).

## 4. ИИ-разбор переписки

### FR-OD-010 (P0). Когда запускается
- В режиме `human` после каждого нового сообщения (входящего или исходящего),
  с задержкой 4 секунды (повторные сообщения в течение задержки объединяются в один
  вызов). В режиме `bot` черновик заполняет бот напрямую, без ИИ.
- Вручную — кнопка «Обновить из чата» в черновике.
- Не запускается для разговоров «Не клиент» и закрытых.

### FR-OD-011 (P0). Порт и адаптер
- Порт `ChatExtractor` в `orders/application/ports.py`: вход — последние сообщения
  разговора (не больше 40 и не старше 7 дней), текущий черновик, дата и время в часовом
  поясе компании, окна доставки и зоны выбранной (или основной) точки, доступные
  букеты дня (название, цена), названия позиций прайса; выход — предложения по полям с
  уверенностью и ID сообщения-источника, список недостающих полей, список фактов
  (для [04](04-chats-and-crm.md), FR-CR-050).
- Адаптер по умолчанию — Claude API через официальный Python SDK `anthropic`;
  модель `claude-opus-5-5` с `effort: low` (задержка и стоимость), структурированный
  вывод по JSON-схеме (`output_config.format`, удобно через `messages.parse` с
  Pydantic-моделью) — точные вызовы сверять с документацией SDK при реализации.
  Проверить на наборе S-04, достаточно ли более дешёвой модели (`claude-haiku-5-5`),
  — решение за сооснователями (Q-12).
- Системная инструкция и описание схемы неизменны и стоят в начале запроса, чтобы
  работало кэширование промпта; изменяемые данные (сообщения, дата, окна) — после.
- Ответ с `stop_reason == "refusal"` или ошибка схемы — черновик не меняется, событие
  пишется в журнал; повторный вызов при следующем сообщении.
- Таймаут вызова 15 секунд, 1 повтор при 429/5xx; при недоступности ИИ черновик
  остаётся ручным, в панели — строка «Автозаполнение временно недоступно».
- Тестовая реализация порта (`FakeChatExtractor`) для тестов без сети.

### FR-OD-012 (P0). Правила применения результата
- ИИ никогда не создаёт заказ, не отправляет сообщений и не меняет поля с `locked=true`
  (правленные человеком или заданные ботом).
- Предложение с низкой уверенностью ставится с `needs_check=true` и подсвечивается
  «уточнить».
- Дата «завтра», «в субботу», «к 10 утра» переводится относительно даты и часового пояса
  компании; время превращается в ближайшее окно точки с подписью «"к 10 утра" →
  ближайшее окно».
- Если в переписке выбран букет дня, которого уже нет, — поле с ошибкой «Букет продан,
  предложите другой».
- Цены позиций черновика всегда берутся из прайса и букетов дня на сервере; ИИ не
  задаёт цену (кроме суммы бюджета, названной клиентом).
- Вызов ИИ запоминает версию черновика и последний ID сообщения. Результат
  применяется только к ещё активному черновику той же версии; после ручной правки,
  нового сообщения, смены точки или создания заказа устаревший ответ не применяется.
  Точное время не заменяется молча интервалом: `requested_time_text` сохраняется,
  предложенное окно требует подтверждения менеджера; бот передаёт такой запрос человеку.
- Изменение черновика рассылается в поток событий (`draft.updated`), правая панель
  обновляется без перезагрузки.

### FR-OD-013 (P0). Приватность
- В ИИ передаются только сообщения разговора и перечисленные справочные данные; не
  передаются другие клиенты, суммы прошлых заказов, данные сотрудников.
- Номера телефонов в тексте передаются как есть (нужны для получателя); логи вызовов
  хранят только метаданные (время, токены, итог), не текст переписки.
- Условия хранения данных у поставщика ИИ проверяются до запуска (Q-13, NFR-PR-005).

### FR-OD-014 (P0). Фото-референсы
- У любого входящего фото в чате — действие «Прикрепить к заказу как пример».
  Прикреплённые фото копируются в фото заказа с видом `reference` при создании заказа и
  показываются флористу в задании («Пример от клиента»), без имени и телефона клиента.

### FR-OD-015 (P0). Геолокация
- Входящая геолокация предлагается в поле адреса (`location` + адрес, если клиент
  подписал точку); курьер видит ссылку «Открыть на карте».

## 5. Интерфейс черновика (по макету)

- Заголовок «Черновик заказа», индикатор «● заполняется из чата».
- Поля: Букет (с подписью «букет дня №1 · забронирован на 30 мин»), Открытка (цена и
  «текст открытки — уточнить»), Повод, Когда (дата и окно с подписью источника), Адрес
  (с «квартира и телефон получателя — уточнить»), Получатель, «Итого».
- Каждое поле редактируется по клику; после правки поле помечается «правка менеджера»
  и больше не меняется ИИ; меню поля «Вернуть автозаполнение».
- Кнопка **«Создать заказ и отправить QR»** (если нужна предоплата) или **«Создать
  заказ»**. Неактивна, пока не заполнены обязательные поля; при наведении — список,
  чего не хватает.
- На телефоне черновик — нижняя панель с кратким описанием, «уточнить: …» и кнопками
  «Создать · 4 900 сом» и «QR».

### FR-OD-020 (P0). Создание заказа из черновика
- Обязательные поля: хотя бы одна позиция, способ получения, дата, окно; для доставки —
  зона, адрес, имя и телефон получателя (как в FR-BT-031); точка.
  Клиент Instagram без своего телефона должен указать телефон получателя для доставки.
- Заказ создаётся существующим сценарием `CreateOrder` в той же транзакции, что и
  `draft.status=converted` под блокировкой черновика; не более одного заказа
  на `draft.id`. Повтор возвращает созданный заказ независимо от изменившейся версии;
  версия проверяется при первом преобразовании, конфликт → 409 с сохранением черновика.
- `source` = канал разговора (`whatsapp` / `instagram`), `created_by` = сотрудник.
- Позиции:
  - позиция прайса — как сейчас;
  - букет дня — системная позиция прайса «Букет дня» (скрыта из выбора), в строке
    заказа снимок названия и цены букета; букет переходит в `sold` после подтверждения
    оплаты или заказа и в `reserved` до этого ([06](06-bot-and-bouquets.md));
  - «Букет по бюджету» — системная позиция с ценой = сумма бюджета и описанием в
    названии строки («Букет на 5 000 сом: пионы, без лилий»).
  - Системные позиции добавляются в прайс миграцией (флаг `system_kind`), архивировать
    их нельзя.
- Статус: `pending`, если требуется предоплата (раздел 6) и её нет; иначе `new`.
- В разговоре — системная строка «Заказ №67 создан» и событие в ленте клиента.
- Если клиент ещё «Новый», этап пересчитывается.

## 6. Предоплата

### FR-PY-001 (P0). Правила компании
Настройки → Компания → «Оплата»:
- Предоплата для доставки: 0 / 50 / 100 % (по умолчанию 100 %).
- Предоплата для самовывоза: 0 / 50 / 100 % (по умолчанию 0 %, Q-02).
- Срок оплаты брони: минуты (по умолчанию 60).
- Текст сообщения с QR (с подстановками `{номер}`, `{сумма}`, `{банк}`).

### FR-PY-010 (P0). «Отправить QR»
- Из черновика (вместе с созданием заказа), из заказа `pending` и кнопкой в поле ввода чата.
- Отправляет в разговор два сообщения: картинку QR точки заказа и текст «Заказ №67 ·
  к оплате 4 900 сом · MBank · Бермет У. Пришлите, пожалуйста, скриншот оплаты».
- Сумма = требуемая предоплата (округление до сома вверх). Если QR у точки нет —
  ошибка FR-MP-008.
- В заказе — событие «QR отправлен» с суммой; у заказа выставляется «ждём чек».

## 7. Чек и проверка оплаты

### FR-PY-020 (P0). Распознавание чека
- Первое входящее изображение (PDF-чеки — P1, пока прикрепляются менеджером вручную как файл разговора) в разговоре, у клиента которого есть заказ
  `pending` с отправленным QR за последние 24 часа, автоматически прикрепляется к этому
  заказу как фото вида `receipt` («чек»). Если `pending`-заказов несколько — к последнему
  с отправленным QR, с возможностью перенести.
- У любого изображения в чате есть действие «Это чек к заказу №…».
- После прикрепления: метка «чек» в списке чатов, уведомление `payment.receipt`, заказ
  появляется в очереди «Проверка оплат». Бот (в режиме бота) отвечает «Спасибо! Проверяем
  оплату, это займёт несколько минут».

### FR-PY-021 (P0). Очередь «Проверка оплат»
- Раздел Заказы → «Проверка оплат N» (и блок в правой панели чата): картинка чека
  (крупно, с увеличением), номер заказа, клиент, к оплате, уже оплачено, поле «Сумма по
  чеку» (заполнено требуемой суммой), способ (`QR`/`перевод`/`наличные`), кнопки
  **«Подтвердить оплату»** и **«Оплата не пришла»**.
- «Подтвердить оплату» записывает оплату существующим сценарием оплат (идемпотентно,
  ключ = ID чека) с заметкой «по чеку», и если оплачено ≥ требуемой предоплаты —
  переводит заказ `pending → new` (FR-OD-003) в той же транзакции.
- После подтверждения: клиенту сообщение «Оплата получена, заказ №67 принят. Статус:
  <публичная ссылка>» (FR-PY-040), уведомление флористам точки, букет дня → `sold`.
- «Оплата не пришла» — клиенту «Пока не видим оплату по заказу №67. Проверьте,
  пожалуйста, перевод или пришлите другой скриншот», разговор переходит в `human`,
  чек помечается «отклонён» (остаётся в истории).
- Подтверждать может только владелец или менеджер точки заказа.
- Подделка: интерфейс показывает подсказку «Сверьте поступление в банковском
  приложении — скриншоты подделывают». Автоматического подтверждения нет.

### FR-PY-022 (P1). Сумма с чека
- ИИ читает сумму и дату с картинки чека и показывает «на чеке: 4 900 сом, 17.10 10:31»
  рядом с полем суммы. Только подсказка; не заполняет поле и не подтверждает оплату.

## 8. Сообщения клиенту по статусам

### FR-PY-040 (P0). Автоматические сообщения
Для заказов, у клиента которых есть разговор в канале (номер для заказов или Instagram):

| Событие | Текст (пример) | Вне окна 24 ч (WhatsApp) |
| --- | --- | --- |
| Заказ подтверждён (`new`) | «Заказ №67 принят на 18 окт, 09:00–11:00. Статус: <ссылка>» | шаблон `order_confirmed` |
| Оплата получена | «Оплата по заказу №67 получена. Спасибо!» | шаблон `payment_received` |
| Готов к самовывозу (`ready`, самовывоз) | «Заказ №67 готов, можно забрать: Токтогула, 125» | шаблон `order_ready_pickup` |
| Курьер в пути (`route`) | «Курьер везёт заказ №67, ожидайте 09:00–11:00» | шаблон `courier_on_way` |
| Вручён (`done`) | «Заказ №67 вручён. Будем рады отзыву: <ссылка>» | шаблон `order_delivered` |

- Публичная ссылка — существующая ссылка статуса заказа (перевыпускается, если
  отозвана).
- В открытом окне — обычный текст; в закрытом — одобренный шаблон подходящего
  назначения. Стоимость проверяется отдельно (FR-CH-030). Переклассифицированный
  в marketing шаблон не используется автоматически в релизе без маркетинговых
  отправок; если подходящего шаблона нет — сообщение не
  отправляется, в истории заказа отметка «Не отправлено: окно закрыто, нет шаблона».
- Для Instagram вне окна — не отправляется (FR-CH-030).
- Владелец включает/выключает каждое событие (Настройки → Бот → «Сообщения по статусам»),
  по умолчанию включены все.
- Клиенту с отказом от сообщений (FR-CH-075) вне окна ничего не отправляется.
- Для заказов, созданных вручную без разговора, сообщения не отправляются (P2).

## 10. Тесты

- Переходы статусов с `pending`: подтверждение, отмена, истечение срока, гонка
  «подтверждение одновременно с истечением» (выигрывает первое под блокировкой);
  срочный заказ на ближайший час, частичная оплата, чек перед истечением, продление.
- Запоздавший ответ ИИ после ручной правки/смены точки/создания заказа не меняет данные.
- `pending` не виден флористу и курьеру, но занимает окно (последнее место окна не
  продаётся второму `pending`).
- Черновик: ИИ не меняет `locked`-поле; двойное нажатие «Создать» — один заказ;
  букет продан между разбором и созданием — ошибка 409 с текстом.
- `ChatExtractor` на наборе 30–50 обезличенных переписок (S-04): точность по полям
  дата, окно, адрес, позиции ≥ 85 % до включения в пилоте.
- Чек: авто-прикрепление к нужному заказу; повторное нажатие «Подтвердить» не создаёт
  вторую оплату; оплата меньше предоплаты не переводит в `new`.
- Сообщения по статусам: окно открыто/закрыто, шаблон есть/нет, отказ от сообщений.
