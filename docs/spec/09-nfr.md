# 09. Нефункциональные требования

Префиксы: `NFR-SE` безопасность, `NFR-PR` приватность и согласия, `NFR-RE`
надёжность, `NFR-PF` производительность, `NFR-OB` наблюдаемость, `NFR-IN`
инфраструктура, `NFR-TS` тестирование, `NFR-UX` интерфейс.

## 1. Безопасность

- **NFR-SE-001 (P0). Изоляция компаний.** Все новые модели содержат `business` (прямо
  или через родителя) и читаются только в рамках `Scope`. Расширить существующие тесты
  изоляции на: разговоры, сообщения, медиа, черновики, букеты дня, уведомления, поток
  событий, сценарии напоминаний, точки, приглашения. Подстановка чужого ID в любом
  поле связи → 404.
- **NFR-SE-002 (P0). Права на сервере.** Матрица ролей из
  [00-product-overview.md](00-product-overview.md) проверяется в сценариях; для
  каждого нового эндпоинта — разрешающие и запрещающие тесты по его матрице,
  включая доступ флориста к букетам дня своей точки; менеджер чужой точки получает 404.
  Карточка общего клиента не обходит ограничения переписки и финансов (FR-CR-047).
- **NFR-SE-003 (P0). Секреты.** Токены Meta шифруются (`TAPME_SECRETS_KEY`), PIN
  регистрации номера — тоже; секреты не пишутся в логи (фильтр логирования по ключам
  `token`, `secret`, `authorization`, `pin`), не возвращаются API, не попадают в
  исключения Sentry/логов.
- **NFR-SE-004 (P0). Вебхуки.** Проверка `X-Hub-Signature-256` в постоянное время;
  ограничение тела 1 МБ; ограничение частоты по IP (300 запросов в минуту) с ответом
  429; эндпоинты вебхуков не принимают сессионные cookie и не требуют CSRF.
- **NFR-SE-005 (P0). Медиа.** Все файлы сообщений и букетов — в закрытом хранилище,
  чтение только через API с сессией и проверкой роли. Изображения перекодируются
  (Pillow), прочие типы отдаются с `Content-Disposition: attachment` и безопасным
  `Content-Type`. Ограничения размеров из [03](03-channels.md).
- **NFR-SE-006 (P0). Приглашения и токены.** Хранятся только хеши; сравнение в
  постоянное время; одноразовые; истекают. Получение страницы приглашения не
  расходует токен; принятие и создание членства атомарны. Внешние ресурсы на странице
  не получают токен через Referer. OAuth подключения канала использует одноразовый
  `state`, привязанный к владельцу, компании, сессии и сроку; callback повторно
  проверяет роль и не доверяет `business_id` из браузера.
- **NFR-SE-007 (P0). Журнал действий.** События с последствиями пишутся в историю:
  подключение/отключение канала, подтверждение оплаты, подтверждение без предоплаты
  (с причиной), объединение клиентов, «Не клиент», смена ответственного, отказ от
  сообщений, изменение сценариев и текстов бота.
- **NFR-SE-008 (P0). Внешний ввод в ИИ.** Текст клиентов — данные, а не инструкции:
  системная инструкция ИИ явно запрещает выполнять указания из переписки; результат
  проходит проверку по схеме и бизнес-правилам (цены с сервера, даты в допустимых
  границах). ИИ не имеет инструментов с побочными эффектами.

## 2. Приватность и согласия

- **NFR-PR-001 (P0). Документы.** На домене Tapme — страницы «Политика
  конфиденциальности» и «Условия использования» (русский; кыргызский — P1), где
  описано: какие данные клиентов магазина обрабатываются (имя, телефон, ник,
  переписка, адреса, даты), зачем, кто обработчик (Tapme для магазина), поставщики
  (Meta, хостинг, поставщик ИИ), сроки хранения, как запросить удаление. Нужны для
  проверки приложения Meta. Юридическая проверка — Q-14.
- **NFR-PR-002 (P0). Запись согласия.** Согласие на напоминания хранится как события
  `ConsentEvent(customer, granted|revoked, source: manual|bot|import|stop_word|reminder_optout,
  channel, text, actor, created_at)`; поле `consent` клиента — производное. Импорт не
  выдаёт согласия (как сейчас).
- **NFR-PR-003 (P0). Минимизация.** В push, Telegram и журналы не попадают телефоны,
  адреса, суммы и текст переписки (только номера заказов и короткие формулировки).
- **NFR-PR-004 (P1). Запрос на удаление.** Владелец удаляет клиента по запросу: заказы
  обезличиваются (имя → «Удалённый клиент», телефон очищается), переписка и медиа
  удаляются, идентичности удаляются. Операция в журнале. Финансовые записи сохраняются.
- **NFR-PR-005 (P0). Поставщик ИИ.** До запуска в пилоте проверить условия хранения
  данных API Claude для организации Tapme и, при необходимости, запросить режим без
  хранения; указать поставщика в политике (Q-13).
- **NFR-PR-006 (P0). Сроки хранения.** Сырые вебхуки — 30 дней; журналы вызовов ИИ
  (метаданные) — 90 дней; переписка и медиа — пока существует клиент (удаление — по
  NFR-PR-004); уведомления — 90 дней. Задачи очистки идемпотентны.

## 3. Надёжность

- **NFR-RE-001 (P0). Нет потерь сообщений.** Проверенный вебхук сохраняется до ответа 200;
  сторож восстанавливает постановку задач из БД после сбоя брокера/процесса. Обработка
  повторяется до успеха (до 10 попыток в течение часа, затем статус `failed` и
  предупреждение). Ручной повтор — команда `reprocess_webhooks --since`.
- **NFR-RE-002 (P0). Нет дублей.** Уникальные внешние ID сообщений, ключи
  идемпотентности для исходящих, заказов из черновика и бота, оплат по чеку.
- **NFR-RE-003 (P0). Исходящие.** Очередь отправки переживает перезапуск воркера:
  `queued` старше 2 минут подхватывает сторож, `sending` с истёкшей арендой
  переходит на сверку в `unknown`. Отсутствие внешнего ID после таймаута не доказывает
  неотправку; сторож не отправляет такой текст повторно вслепую (FR-CH-020).
- **NFR-RE-004 (P0). Отказ зависимостей.**
  - Meta недоступна — входящие ждут повтора Meta; исходящие повторяются; в CRM плашка
    «WhatsApp временно не отвечает». Автоповтор — только для безопасных случаев
    FR-CH-020; при `unknown` показывается необходимость проверки отправки.
  - ИИ недоступен — черновик ручной (FR-OD-011).
  - Redis недоступен — поток событий падает, интерфейс переходит на опрос (FR-NT-011);
    Celery-задачи ждут восстановления.
- **NFR-RE-005 (P0). Время.** Все задачи по расписанию (снятие броней, истечение
  оплаты, эскалации, конец дня букетов) идемпотентны и выдерживают пропуск запуска.

## 4. Производительность

| Требование | Цель |
| --- | --- |
| NFR-PF-001 (P0) Ответ на вебхук | p95 ≤ 300 мс, максимум 1 с |
| NFR-PF-002 (P0) Сообщение клиента видно в открытом чате | p95 ≤ 3 с от получения вебхука |
| NFR-PF-003 (P0) Ответ бота | p95 ≤ 3 с от получения вебхука (без учёта Meta) |
| NFR-PF-004 (P0) Отправка из CRM до статуса `sent` | p95 ≤ 2 с |
| NFR-PF-005 (P0) Обновление черновика ИИ | p95 ≤ 8 с после последнего сообщения |
| NFR-PF-006 (P0) Список «Чаты», «Клиенты» (50 строк) | p95 ≤ 400 мс на сервере при 20 000 клиентов и 200 000 сообщений в компании |
| NFR-PF-007 (P0) Push | ≤ 2 с от события до отправки в сервис push |

Нагрузка пилота мала (десятки разговоров в час), но индексы закладываются сразу:
`Message(conversation, sent_at)`, `Conversation(business, mode, waiting_since)`,
`Conversation(business, last_message_at)`, `CustomerRecord(business, stage)`,
`ChannelIdentity(channel, external_id)`, `BouquetOfDay(point, shift_date, status)`.

## 5. Наблюдаемость

- **NFR-OB-001 (P0). Журналы** в структурированном виде (JSON) с `business_id`,
  `request_id`, `task_id`; без персональных данных (NFR-PR-003).
- **NFR-OB-002 (P0). Счётчики** (выводятся на служебной странице владельца Tapme и в
  логах): вебхуки получено/ошибок, сообщения в очереди отправки и их возраст, ошибки
  отправки по кодам Meta, время ответа бота, вызовы ИИ и их длительность/ошибки,
  push отправлено/ошибок.
- **NFR-OB-003 (P0). Проверки здоровья.** `/health/` дополняется: Redis, Celery
  (возраст последнего «пульса» воркера и beat), возраст старейшего `queued` сообщения.
- **NFR-OB-004 (P1). Ошибки** отправляются в сервис мониторинга ошибок (Sentry или
  аналог) с фильтрацией секретов и персональных данных.
- **NFR-OB-005 (P0). Предупреждения команде Tapme** в Telegram: вебхуки не приходят
  больше 30 минут у активного канала в рабочие часы; очередь отправки старше 5 минут;
  доля ошибок ИИ > 20 % за час.

## 6. Инфраструктура

- **NFR-IN-001 (P0). Публичный HTTPS.** Рабочий сервер с доменом и HTTPS (Caddy, как в
  `compose.production.yaml`) — обязательное условие для вебхуков Meta и push.
  Вебхуки: `https://<домен>/api/v1/webhooks/meta/whatsapp/` и `/instagram/`.
- **NFR-IN-002 (P0). ASGI.** Поток событий (SSE) работает под ASGI: API запускается
  Gunicorn с Uvicorn-воркерами (или отдельный ASGI-сервис для `/api/v1/stream/`).
  Caddy настраивается без буферизации для SSE (`flush_interval -1`), таймаут простоя
  ≥ 120 с.
- **NFR-IN-003 (P0). Очереди Celery:** `webhooks`, `outbound`, `media`, `ai`,
  `notifications`, `default`. Отдельные воркеры или пул с приоритетом для `webhooks` и
  `outbound`. Beat-задачи: снятие броней (раз в минуту), истечение оплаты (раз в минуту),
  эскалации (раз в минуту), сторож исходящих (раз в минуту), конец дня букетов (раз в
  15 минут), этапы клиентов (03:00), автоскрытие «Новых» (03:30), очистка (04:00),
  обновление токенов Instagram (ежедневно), синхронизация шаблонов (ежедневно),
  существующая очередь напоминаний (раз в 15 минут).
- **NFR-IN-004 (P0). Redis** — брокер Celery, pub/sub для потока событий, журнал
  событий за 5 минут для переподключения. С `appendonly` (как сейчас).
- **NFR-IN-005 (P0). Переменные окружения** добавляются в `.env.production.example`:
  `TAPME_SECRETS_KEY`, `META_APP_ID`, `META_APP_SECRET`, `META_WEBHOOK_VERIFY_TOKEN`,
  `META_CONFIG_ID`, `META_GRAPH_VERSION`, `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`,
  `VAPID_SUBJECT`, `TELEGRAM_BOT_TOKEN`, `ANTHROPIC_API_KEY`, `TAPME_AI_MODEL`
  (по умолчанию `claude-opus-5-5`), `TAPME_AI_ENABLED`.
- **NFR-IN-006 (P0). Резервные копии** (`scripts/backup.py`) включают новые таблицы и
  медиа сообщений и букетов; проверка восстановления (`verify_backup.py`) расширена.
- **NFR-IN-007 (P0). Стенды.** Локально — тестовый номер Cloud API и тестовый аккаунт
  Instagram на отдельном приложении Meta «Tapme Dev»; вебхуки на локальную машину — через
  туннель (только для разработки). Рабочее приложение Meta не используется для разработки.

## 7. Тестирование

- **NFR-TS-001 (P0).** Доменные правила (бот, этапы, окно 24 часа, бронь, правила
  напоминаний, получатели уведомлений) — unit-тесты без Django.
- **NFR-TS-002 (P0).** Порты с тестовыми реализациями: `MetaClient` (Graph API),
  `ChatExtractor` (ИИ), `PushSender`, `TelegramSender`, `MediaDownloader`; контрактные
  тесты для каждой пары «двойник / реальный адаптер» (реальный — с записанными ответами).
- **NFR-TS-003 (P0).** Фикстуры вебхуков Meta (`tests/fixtures/meta/`) — каждый тип и
  граничные случаи; тест-генератор подписи.
- **NFR-TS-004 (P0).** Конкурентность на PostgreSQL: бронь букета, первый ответ
  (ответственный), подтверждение оплаты vs истечение, последнее место окна с `pending`.
- **NFR-TS-005 (P0).** Сквозные Playwright-сценарии (Chromium и Firefox, 1440 и 390):
  1) бот → заказ → QR → чек → подтверждение → флорист видит; 2) человек в чате →
  черновик → заказ; 3) напоминания утром; 4) переключение точек; 5) первый вход
  флориста. Внешние сервисы — двойники через тестовый эндпоинт, включаемый только в
  тестовых настройках.
- **NFR-TS-006 (P0).** Набор для ИИ (S-04): 30–50 обезличенных переписок с ожидаемыми
  полями; прогон перед каждым изменением промпта или модели; порог ≥ 85 % по полям
  дата, окно, адрес, позиции.

## 8. Интерфейс

- **NFR-UX-001 (P0).** Все новые экраны работают на ширине 390 без горизонтальной
  прокрутки; зоны нажатия ≥ 44 px на телефоне.
- **NFR-UX-002 (P0).** Стиль — существующие токены CRM (шрифт Golos Text, тёмно-зелёное
  меню, фиолетовый акцент только для основных действий, зелёный WhatsApp — только для
  WhatsApp-действий, розовый — только для Instagram).
- **NFR-UX-003 (P0).** Состояния загрузки, пустые, ошибки и «нет доступа» для каждого
  нового экрана; тексты ошибок на русском без технических кодов (код — в подсказке).
- **NFR-UX-004 (P0).** Доступность: управление с клавиатуры в чате (Enter — отправить,
  Shift+Enter — новая строка), видимый фокус, подписи для иконок-кнопок.
