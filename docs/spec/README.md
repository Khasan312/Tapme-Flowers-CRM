## Воспроизведение макетов

Это статичные эскизы будущего релиза, а не подключённые экраны CRM. Сначала
установите зависимости frontend по корневому README (Node.js 20.19+ или 22.12+).
Из корня репозитория:

```sh
python3 design-reminders/v2/build_v2.py
python3 design-crm/build_crm.py
python3 design-onboarding/build_onb.py
cd frontend
npx playwright install chromium
cd ..
NODE_PATH=./frontend/node_modules node design-reminders/v2/shoot.cjs
NODE_PATH=./frontend/node_modules node design-crm/shoot.cjs
NODE_PATH=./frontend/node_modules node design-onboarding/shoot.cjs
```

HTML открывается через `file://`; отдельные Chrome и сервер на порту 8765 не нужны.
Снимки создаются в `png/` соответствующего каталога; для проверки без замены
публикуемых PNG задайте `MOCKUP_OUTPUT_DIR=/tmp/tapme-design-review/<группа>`.
В макетах подключены Google Fonts: без сети браузер использует запасной шрифт.
Мобильные макеты нарисованы как телефоны на презентационном холсте 1440×900;
адаптивность рабочего интерфейса проверяется при реализации.

Результаты проверки этого PR: [review-2026-10-17.md](review-2026-10-17.md).
Открытые продуктовые решения остаются в [11](11-open-questions-and-risks.md):
слияние ТЗ не означает готовность каналов к запуску.

## Как читать требования

- **Приоритет.** `P0` — без этого релиз не выпускаем. `P1` — делаем сразу после P0
  в этом же релизе, если хватит времени. `P2` — не делаем, но архитектура не должна мешать.
- **Критерии приёмки** записаны как «Дано / Когда / Тогда» или списком. Каждый
  критерий проверяется отдельно: автотестом, где возможно, иначе ручной проверкой.
- **Ссылки.** `D-07` — решение из журнала в [00-product-overview.md](00-product-overview.md),
  `FR-CH-012` — требование, `T-14` — задача в [10-roadmap.md](10-roadmap.md),
  `Q-05` — открытый вопрос.
- **Слова «должен», «не должен», «может»** означают обязательное требование,
  запрет и допустимое, но не обязательное поведение.
- Названия экранов и кнопок в кавычках — точный текст интерфейса, если не сказано
  «например».

## Правила для разработки (людей и ИИ-агентов)

1. Перед задачей прочитать: `docs/ARCHITECTURE.md`, этот README, файл ТЗ своей
   фичи, `SESSION_HANDOFF.md` (последние записи).
2. Соблюдать слои модульного монолита: `domain.py` без Django, сценарии в
   `application/` через Protocol-порты, ORM только в `infrastructure/`, HTTP в
   `api.py`. Тест импортов слоёв не должен падать.
3. Каждый новый сценарий получает `Scope(user_id, business_id)` и проверяет членство
   и роль на сервере. Видимость кнопок — не защита.
4. Любая запись в двух модулях — через публичные контракты в одной транзакции.
   Повтор запроса с тем же ключом идемпотентности не создаёт дублей.
5. Деньги — `Decimal` и десятичные строки в API. Время хранить в UTC, показывать в
   часовом поясе компании (по умолчанию `Asia/Bishkek`).
6. Секреты (токены Meta, ключи) не попадают в Git, логи, ответы API и чат.
7. Не расширять рамки задачи. Если требование неоднозначно — остановиться, записать
   вопрос в [11-open-questions-and-risks.md](11-open-questions-and-risks.md) и спросить.
8. В конце задачи — обновить `SESSION_HANDOFF.md`: что сделано, что проверено,
   что не проверено.

### Определение готовности (Definition of Done) для любой задачи

- [ ] Все критерии приёмки связанных `FR-…` выполнены и перечислены в отчёте.
- [ ] Новые доменные правила покрыты unit-тестами без Django.
- [ ] Сценарии покрыты интеграционными тестами на PostgreSQL, включая изоляцию
      двух компаний и матрицу ролей для новых эндпоинтов.
- [ ] Проходят: `uv run pytest -q`, `uv run mypy`, `uv run ruff check .`,
      `uv run ruff format --check .`, `uv run python manage.py makemigrations --check --dry-run`,
      `uv run python manage.py spectacular --validate --fail-on-warn --file /tmp/tapme-openapi.yaml`.
- [ ] Фронтенд: `npm run build`, `npm run format:check`; для изменённых экранов —
      Playwright-сценарий (Chromium и Firefox), ширины 1440 и 390 без горизонтальной прокрутки.
- [ ] Миграции обратимы или явно помечены необратимыми с планом отката.
- [ ] Обновлены `README.md`/`docs/` там, где меняется запуск или эксплуатация.

## Шаблоны промптов для ИИ-агентов

**1. Технический план задачи (до кода):**

```text
Ты работаешь в репозитории Tapme Flowers CRM. Прочитай docs/ARCHITECTURE.md,
docs/spec/README.md, docs/spec/<файл фичи>.md и задачу <T-xx> в docs/spec/10-roadmap.md.
Не пиши код. Составь план в docs/spec/plans/<T-xx>.md: изменения моделей и миграций,
порты и сценарии, эндпоинты API с примерами запросов и ответов, изменения
интерфейса, список тестов по каждому критерию приёмки, риски. Отметь требования,
которые неясны, и вопросы к нам.
```

**2. Реализация по утверждённому плану:**

```text
Реализуй задачу <T-xx> по плану docs/spec/plans/<T-xx>.md и требованиям
<FR-…>. Соблюдай правила разработки из docs/spec/README.md. Пиши тесты к каждому
критерию приёмки. В конце запусти все проверки из «Определения готовности»,
приложи вывод, перечисли выполненные критерии и обнови SESSION_HANDOFF.md.
Не делай commit/push, пока мы не попросим.
```

**3. Проверка готового результата:**

```text
Проверь ветку по задаче <T-xx>: для каждого требования <FR-…> найди код и тест,
которые его выполняют, и отметь «выполнено / частично / нет» с путём к файлу.
Отдельно проверь изоляцию компаний, роли и идемпотентность. Ничего не исправляй —
только отчёт.
```

## Как менять ТЗ

- Новое требование добавляется с новым номером; номера не переиспользуются.
- Отменённое требование помечается ~~зачёркнутым~~ с причиной и датой.
- Любое изменение рамок фиксируется в журнале решений
  ([00-product-overview.md](00-product-overview.md#6-журнал-решений)) с датой.
- Добавление в P0 возможно только вместе с удалением другого P0 или переносом сроков.
